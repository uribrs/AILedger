# Code reviewer — pass 1

## Summary
The new code is generally clean, idiomatic C#, and consistent with the surrounding `CortexXdr/` conventions: file-scoped namespaces, sealed types, async/await with `ConfigureAwait(false)`, and defensive parsing using `System.Text.Json`. `JsonNode` ownership is handled carefully (deep-cloning before reparenting, detaching children into fresh arrays), and there are no obvious null-deref or file-handle leaks. The main concerns are (1) the `va_endpoints` XQL is fetched twice end-to-end, (2) the asset projection emitted alongside findings will be sparse because the `va_endpoints` query only selects 5 columns, and (3) `BuildFindingIdsByEndpointIdAsync` does not de-duplicate CVEs across multiple rows for the same endpoint, so emitted assets can carry duplicate `finding_ids`. There are no tests covering any of the new mapping/parsing logic.

## Must fix
- `Integrations/CortexXdr/CortexXdrProbeRunner.cs:177` and `:329` — the same `dataset = va_endpoints | fields endpoint_id, endpoint_name, cves, severity, severity_score | limit N` query is executed end-to-end twice (once to build `findingIdsByEndpointId`, once again inside `ProbeEmitFindingsAsync`). Cache the row array on the first call and pass it down (e.g., return `(Dictionary<string, JsonArray> map, JsonArray rows)` from `BuildFindingIdsByEndpointIdAsync` or hoist `FetchXqlRowsAsync(BuildVaEndpointsQuery(...))` into `ExecuteAllAsync` and pass `endpointRows` into both helpers). Each XQL round-trip costs `PollIntervalSeconds` of latency minimum, so this also halves the wall time of the emit phase.
- `Integrations/CortexXdr/CortexXdrProbeRunner.cs:191-200` — within `BuildFindingIdsByEndpointIdAsync`, `.Distinct()` only de-dupes CVEs inside a single row. If `va_endpoints` returns more than one row for the same `endpoint_id` (XQL aggregations can do this, and a re-run of the same probe inside a session would too), duplicate `finding_ids` end up in the per-endpoint `JsonArray` and propagate into the emitted asset. De-dupe per endpoint instead — e.g., track a `HashSet<string>` of CVE IDs per `endpointId` alongside the `JsonArray`, or de-dupe with a final pass before returning.
- `Integrations/CortexXdr/CortexXdrProbeRunner.cs:548-549` — `BuildVaEndpointsQuery` only selects `endpoint_id, endpoint_name, cves, severity, severity_score`. `MapFindingResult` then passes the row to `MapAsset` (via `CortexXdrEmitMapper.cs:61`), which reads `os_version`, `endpoint_type`, `first_seen`, `last_seen`, `ip`, `mac_address`, `tags`, `domain`, `group_name` — none of which exist in the projection. The emitted `asset` inside each finding will be largely null, which defeats the point of producing a collector-shaped emission. Either widen the `va_endpoints` projection to include the asset columns the collector pulls, or have `ProbeEmitFindingsAsync` look up the corresponding endpoint object from the `/get_endpoint` payload (already fetched in `ProbeEmitAssetsAsync`) and pass that into `MapAsset`.

## Should fix
- `Integrations/CortexXdr/CortexXdrProbeRunner.cs:43,74-83` — `FetchDatasetsArrayAsync` POSTs to `/xql/get_datasets` a second time even though `ProbeDatasetInventoryAsync` already fetched it a few lines earlier. The second call could be avoided by having `ProbeDatasetInventoryAsync` return both the `ProbeRunItem` and the parsed `JsonArray`, or by stashing the previous response body and reusing it. Minor on a probe, but it's redundant network traffic against a credentialed endpoint.
- `Integrations/CortexXdr/CortexXdrProbeRunner.cs:618` — `Task.Delay(PollIntervalSeconds)` is called *before* the first poll. For queries that complete instantly (and Cortex often does), this wastes a full interval. Either issue the first `get_query_results` before sleeping, or model the loop as `do { request; if (done) return; await delay; }`.
- `Integrations/CortexXdr/CortexXdrProbeConfigurationBuilder.cs:52-60` — `NormalizeBaseUrl` constructs `new UriBuilder(Uri.UriSchemeHttps, host)` with no `Port`, silently dropping any port the user supplied in the original FQDN/URL. If a user passes `https://api-foo.bar:8443`, the probe will hit `https://api-foo.bar/`. Either preserve `uri.Port` (when it is not the default) or document/validate that ports are not supported.
- `Integrations/CortexXdr/CortexXdrEmitMapper.cs:33` — `["os_build"] = NullableString(osVersion)` simply copies the full `os_version` value into both `os_version` and `os_build`. The collector likely distinguishes the build number; either parse out the build segment from the OS version, or set `os_build` to `null` and let the parser derive it, but don't carry the same string under two contract names without a comment.
- `Integrations/CortexXdr/CortexXdrProbeRunner.cs:587-606` — `AsStringOrNull` here duplicates `AsString` in `CortexXdrEmitMapper.cs:369-388` exactly. Promote one of them to an internal helper class (e.g., `CortexXdrJsonHelpers`) and share. Same comment for `TryParseNode` (runner) vs `TryParseJson` (mapper).
- `Integrations/CortexXdr/CortexXdrProbeRunner.cs:282-301` and `:372-407` — `await using StreamWriter writer = new(fs)` followed by `await using FileStream fs = new(...)` double-disposes the underlying stream (StreamWriter owns it by default). It works because `FileStream.Dispose` is idempotent, but the conventional pattern is to construct the StreamWriter with the path directly, or pass `leaveOpen: true` on one side. Cosmetic, but worth fixing while the code is fresh.
- `Integrations/CortexXdr/CortexXdrProbeRunner.cs:298,403` — `WriteLineAsync` uses the platform's default line terminator (`Environment.NewLine`). NDJSON consumers usually expect LF; on a Windows runner this writes CRLF and some downstream JSONL parsers reject it. Either set `writer.NewLine = "\n"` or use `WriteAsync(json + "\n")`.

By the time the loop exits without `return`, the previous iteration already evaluated status; just track that boolean to avoid the extra `JsonDocument.Parse` on exit.

- `Integrations/CortexXdr/CortexXdrEmitMapper.cs:159` — `raw!.StartsWith('[') || raw.StartsWith('{')` uses `!` even though `string.IsNullOrWhiteSpace(raw)` already returned. - `Integrations/CortexXdr/CortexXdrProbeConfiguration.cs:5-7` — `DefaultPollTimeoutSeconds = 120` while builder clamps to `max: 900` (`CortexXdrProbeConfigurationBuilder.cs:31`). Fine, but the clamp bounds are also magic numbers — consider hoisting them next to the defaults.
