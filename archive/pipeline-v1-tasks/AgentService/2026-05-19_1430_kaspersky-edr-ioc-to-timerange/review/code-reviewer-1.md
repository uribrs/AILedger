## Important
- **I1** — `Source/Application/Cymulate.Agent.Application.Actions/Actions/QueryIntegration/Logic/Clients/EDR/Kaspersky/KasperskyEdrApi.cs:298-304` — `createEventProcessingTaskAsync` still sets `requestDetails.Query = string.Empty`. With the IOC path gone there is no IOC string to store, but the time-range filter values (the `From`/`To` range and `Hostname`) are now the only thing identifying the request, and they are lost from `KeywordRequestDetailsModel` aside from being inside `Body`. Consider populating `Query` with something useful for debugging (e.g. `$"{iTimeRangeGroup.Hostname} {iTimeRangeGroup.DateTimeRange.From:o}..{iTimeRangeGroup.DateTimeRange.To:o}"`) so the request-details surfaced in cache errors are not empty. The previous code put `iIocGroup.Query` here; the replacement loses that breadcrumb entirely.

## Suggestions
- **S1** — `Source/Application/Cymulate.Agent.Application.Actions/Actions/QueryIntegration/Logic/Clients/EDR/Kaspersky/KasperskyEdrApi.cs:355-356` — `KLEVP_EVENT_HOST_NETBIOSNAME` is always set to `iTimeRangeGroup.Hostname`, even when the value is empty/whitespace. `QueryGroupBase.Hostname` is `required string` but the project conventions in this codebase sometimes seed it as `""` for unscoped queries. An empty NETBIOS filter on the Kaspersky side may return zero results silently. Worth either guarding (`if (!string.IsNullOrWhiteSpace(iTimeRangeGroup.Hostname))` then add the key) or confirming with the Kaspersky API contract that empty == match-all. The IOC version had a meaningful `EVP_FTX_QUERY` term that covered the empty-host case; removing it changes effective behavior.
- **S2** — `Source/Application/Cymulate.Agent.Application.Actions/Actions/QueryIntegration/Logic/Clients/EDR/Kaspersky/KasperskyEdrApi.cs:325-326`, `333-334`, `341-342` — `createEventProcessingTaskAsync` logs the error and then stores the same string in `resultObj.ErrorMessage` (later re-thrown one frame up at L203 and re-logged in `fetchAlertsAsync` catch). The end result is the same line logged twice. Consider letting the caller log and just returning the result object, or skip the inner log to avoid duplicate noise. Not introduced by this change — but the new `queryByTimeRange` wrapper at L165 adds a third log of effectively the same failure. Worth pruning while the file is open.
- **S3** — `Source/Application/Cymulate.Agent.Application.Actions/Actions/QueryIntegration/Logic/Clients/EDR/Kaspersky/KasperskyEdrApi.cs:215-216` — The error log in `fetchAlertsAsync` is now keyed by `Hostname` and `DateTimeRange`. If multiple `QueryIds` are merged into a single time-range group (which `DateTimeRangeQueriesMaker` does), adding `string.Join(",", iTimeRangeGroup.QueryIds)` to the log would make it possible to map a failure back to the originating contract IDs. Same applies to the L191 info log.
- **S4** — `Source/Application/Cymulate.Agent.Application.Actions/Actions/QueryIntegration/Logic/Clients/EDR/Kaspersky/KasperskyEdrApi.cs:165-174` — `tryWriteCacheDetailError` is called from the outer `queryByTimeRange` catch and `fetchAlertsAsync` already writes a cache-detail error on the same `iCacheWriter` in its own catch (L218-223). If `fetchAlertsAsync` itself completes its catch path successfully and rethrows nothing, the outer catch won't fire — fine. But if `createNotSupportedResultTypeException` is thrown (L154) we end up with one error row, which is correct. Worth a quick mental check that double-writing for a single failure can't happen now that both layers catch `Exception`.
- **S5** — `Source/Application/Cymulate.Agent.Application.Actions/Actions/QueryIntegration/Logic/Clients/EDR/Kaspersky/KasperskyEdrApi.cs:161` — `.GetAwaiter().GetResult()` is preserved from the prior code (the base callback is `void`), so no new sync-over-async is introduced. Flagging only to confirm intent matches the rest of the file (e.g. L106 in `tryHandleApiCallError`).

## Open questions
- Does Kaspersky's `EventProcessingFactory.CreateEventProcessing2` interpret an empty `KLEVP_EVENT_HOST_NETBIOSNAME` as "no filter" or as "match empty hostname"? This determines whether **S1** is a behavior bug or a non-issue.
- Was the loss of the IOC filter (`EVP_FTX_QUERY`) deliberate at the manager-contract level, or did the upstream just stop sending IOC queries and we now rely on the manager to post-filter alerts after time-range pull? If the latter, the missing `Query` field in `requestDetails` (see **I1**) is even more important for traceability.
