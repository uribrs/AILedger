# Decisions

- Branch off `origin/dev` (`ad2699a`), not local `dev` (2 behind) and not `absorb/sdk-source` (already merged, 0 ahead).
- The content hash is a carry, not a droppable diagnostic — operator ruling: it is how a stuck collector re-uploading identical content is detected (DefenderVm precedent).
- Batch-scoping opt-in is an emitter CONSTRUCTION flag, not a per-call parameter — it is a per-run collector capability, constant for the run's life, and matches the options-freeze-at-construction shape `Create` already establishes.
- Scoping folds into the two generic page methods only; the four named page methods inherit it by delegation.
- Batch-level `PublishAsync`/`PublishUtf8Async` stay unscoped — they take an explicit target path and are not page publishes.
- `SessionAuthRetry` carries verbatim as a static; DESIGN.md's static taxonomy sanctions explicit-args statics, so no reshape is owed.
- `ContentHashHex` does NOT go on `PublishResult` in this task — that is an SDK-surface change owned by the SDK-absorption task.
- The two pinned `instanceBatchId` assertions are W1's to flip, not the seam's to pre-fix — the seam gate tolerates exactly those two failures so the regression's blast radius stays visible in one place.
- Emission docs (`README.md`, `README.Publishing.md`) are W1's exclusive files; Conversation docs are W2's; W3 is tests-only. This keeps file-touch partitioning clean without a docs worker.
- Both accepted limits (A7 consumer-side AdvancePage ordering, A8 no concurrency safety under scoping) get documented on the ctor flag rather than engineered away.
- **Scope release moved into a `finally` (operator ruling, 2026-07-30) — a deliberate DEVIATION from Shared, not parity.** Shared's consumers restore only on a dud page and leave the scope set when a publish throws. The emitter now releases on failure too, so the invariant is "a batch scope survives only a page that actually produced records." Rationale: a collector that swallows the publish exception and advances anyway would otherwise announce a batch folder that upstream parses and finds empty (the aborted multipart uploaded nothing). Safe because release is idempotent and the batch path derives from the preserved base URL + page number, so a retry of page N re-derives the identical folder and identical id — pinned by two tests.
- `BuildMandatoryTargetPath` runs BEFORE `BeginBatchScope`: validate the output name before mutating the progress context, so an invalid name never scopes-then-unscopes.
- `EndBatchScope(progressContext, result)` renamed to `ReleaseBatchScope(progressContext)` — with the `finally` the condition is a single flag, so the helper no longer inspects `PublishResult`.
- Test assertions for `instanceBatchId` derive from `BuildBatchInstanceId(BaseUrl, N)` rather than hardcoded UUID literals; the golden-vector literal lives in exactly one test (W1's improvement on the brief).
- **M1 (code-reviewer, Major) — FIXED 2026-07-30 on operator direction; the escalation below was my misjudgement, since the scope fence forbids MODIFYING the adapters repo, not READING it.** `pageNumber` is trusted from the caller and never reconciled against `AdapterProgressContext.CurrentPage`, so a collector whose publish page number is a loop-local counter rather than the run's absolute page would, after a resume, overwrite an earlier attempt's object AND re-announce that attempt's `instanceBatchId` — silently converging two different record sets onto one document under the store's unique index. Not fixed here for three reasons: (a) it is a PRE-EXISTING property of Shared's `BatchScopedStorage`, not a regression introduced by this carry; (b) the fix is a throw or warning whose correctness depends on the caller-page ↔ `CurrentPage` relationship being uniform across collectors, which is unverified and lives in the adapters repo that this task is scope-fenced out of; (c) FalconFindingsFlow passes an `outputPage` that is visibly not the progress page, so a naive guard could break a shipping collector. Correct next step is a separate task that first establishes the contract across all four batch-scoped consumers, then enforces it.
- **M1 resolution: `BeginPage` throws when `pageNumber < CurrentPage`.** Verified first that all three batch-scoped consumers seed their page counters from resume state (so M1 was latent, not active) and that three different page/watermark relationships exist — Falcon `page == CurrentPage + 1`, Qualys/IVMC `page == CurrentPage`, and Qualys/IVMC also never call `RestoreProgress` so `CurrentPage` stays at its default. The reviewer's first suggestion (`page != CurrentPage`) would have broken Falcon; `page < CurrentPage` admits all three and still catches the restart-at-1-on-resume case. Guard lives in `BeginPage`, not the emitter, so it travels with the identity derivation. Pinned by a regression theory over all three relationships.
- Rejected an alternative guard that tracked already-scoped page numbers per context: a collector legitimately re-scopes page N when retrying a failed page, so it would fire on the exact path `..._AfterAFailedPage_RetryReusesTheSameFolderAndId` proves is correct.
